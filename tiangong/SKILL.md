# 天工 · AI 协作开发手册

明宋应星著《天工开物》，收录农工百艺之法，图说并重，后人按图可循、依法可造。本技能取名"天工"：开发如开物——先明法度，后施巧艺。它把与 AI 协作开发产品的九阶段流程法典化，使 agent 不靠灵感推进项目，而按约定好的工序、交付物与通过标准一步步营造。

## 何时遵循本法式

本手册**仅在用户明确调用时启用**：

- 用户说"按天工来""按天工流程开发""按手册开发""按流程开发"；
- 用户点名本手册的九阶段之一，或任一工件（立项书、需求规格、选型比选表、接口约定、项目备忘、演示说明、通检表、验收自测表……）；
- 已在法式流程中的项目继续推进。

用户开始新项目、产品或仓库，任务有多个步骤，本身**不构成**启用理由；小修小补、单文件问答不启用本手册。

**用户要求跳过流程时**：用户说"不用走流程了""直接改"之类，即停止阶段推进与补齐工件，只保留"任务四要素""排错五项""安全最低集"（见下文）；已生成的工件留在仓库不动。用户随时可说"回到天工流程"，按"如何定位当前阶段"从最早缺失交付物的阶段继续。

**指令优先**：本法式任何环节、任何纪律与用户指令冲突时，一律以用户指令为准。

## 五条总纲（凌驾于一切阶段之上）

1. **先约定，后生成。** 需求、结构、接口先写成文档放进仓库，代码按约定生成。约定未写明之处，不得各自猜测。
2. **一次一小步。** 单次任务只做一个可核对的增量；先写如何验收，再动手；核对无误后再扩展。禁止"把剩余功能一次性生成"——一旦失败，无法定位是哪一步引入的问题。
3. **形容词不算验收。** 验收必须写成"给定—当—则"（Given-When-Then），能按步骤判出过或不过。"更智能""体验更好"不算验收。
4. **一切留痕于仓库。** 约定、计划、日志、结论写入仓库文件（docs/），不依赖对话记录。对话越长，模型越容易丢掉早先约定或混入已作废的结论。
5. **人定机做。** 选哪道题、边界画在哪、怎样算通过、能否造数据、密钥怎么处理，由人决定；按已写清的范围起草文档与代码，由模型完成。遇到越界决定须向用户提出，不得自行拍板。

## 触发后的第一动作

1. 若项目已有 `docs/CONSTITUTION.md`（项目铁律）与 `docs/PROJECT_MEMO.md`（约定总汇），先读它们。
2. 按"如何定位当前阶段"确定阶段，读对应参考文件（见文末路由表）。
3. 把当前任务补全为四要素（缺项向用户确认），写入按次计划。
4. 按"计划—执行—核对"推进；结束时更新备忘与开发日志。

## 任务四要素（每个任务，无论谁下达）

向模型下任务（含给自己拆任务）必须写清四项，缺一项先补全确认再动手：

- **约束**：不能做的事。例：不得引入备忘未记录的新依赖；不得提交密钥。
- **需求**：必须做的事。例：实现"提交代码并查看状态"对应的提交接口。
- **范围**：允许改动的文件或目录。例：只改 `services/submission/` 与 `docs/contracts/`。
- **输出**：交什么、怎样算对。例：接口返回 201 且含 `submission_id`；自测命令通过。

较差："帮我做一个完整的高可用系统，要现代。"
较好："约束：单人、两周、技术栈限 Node.js。需求：实现提交与状态查询两个接口。范围：只改 services/ 与接口约定文档。输出：通检中两条路径可跑通，接口约定补上成功与失败示例。"

## 九阶段总览

| 阶段 | 关键交付物 | 通过标准 |
|---|---|---|
| 一 立项需求 | 立项书、需求规格（必做/不做、用户故事、验收句） | 每条必做有可按步骤核对的验收句；不做事项写清 |
| 二 结构选型 | 架构说明（模块职责表、需求→模块对照、选型比选表） | 核心需求均有负责模块；能说清为何放弃落选方案 |
| 三 数据约定 | 数据模型、接口约定（成功+失败例）、项目备忘初稿、总计划初稿 | 约定覆盖主路径；临时假实现已标明 |
| 四 工程起步 | README、.gitignore（逐条说明）、≥3 次小步提交、审查纪要 | 他人可按 README 跑通首跑；初始改动已通读 |
| 五 主路径贯通 | 端到端主路径（允许标明的假实现）、演示说明、差距清单 | 他人可按说明复现主路径；差距可排期可验收 |
| 六 核心推进 | 可独立验证的增量、自测命令、交叉审阅问题单、开发日志 | 每块可独立验证；问题已关闭或有遗留说明 |
| 七 联调排错 | 通检表（≥5 条含 1 条异常）、联调记录 | 通检通过；致命问题当次清零 |
| 八 交付准备 | 回归结果、验收自测表、安全清单、交付演练 | 重要缺陷清零；自测每项有结论有凭据 |
| 九 结项复盘 | 完成情况对照表、方案与验证、分工与复盘 | 必做逐条有结论；材料可独立阅读核查 |

## 如何定位当前阶段

1. 用户明说阶段或环节，从之。
2. 否则查看 docs/ 工件（见"仓库工件布局"），从**最早缺失的交付物**所在阶段进入；进入后先补齐该阶段交付物再继续。
3. 已有仓库但无任何工件：回到阶段一，先补立项需求与备忘，再继续编码。不得在无约定的情况下直接堆代码。

阶段可按项目大小压缩或并行，但顺序不可颠倒：约定未定不生成、主路径未通不做细枝、未通读的改动不合入。

## 增补与新一轮迭代

- **一步能搞定的小增补**：在总计划（`docs/plan/PLAN.md`）末尾顺延编号追加一步，写对应按次计划，做完勾掉；不必重走立项。
- **新一轮迭代或大量增补**：回到阶段一，重新走立项、需求、结构……的循环。已有工件（项目宪法、立项书、需求规格、备忘等）**不新建、不删除**：需要补充的在原文件末尾追加（如立项书末尾加"第 N 轮增补"一节），原内容一律保留；宪法条文变动仍须经用户批准并记变更。
- 每轮迭代开工前，先读一遍已有工件，明确本轮改什么、不动什么。

## 跨阶段纪律

**项目铁律（CONSTITUTION）**：本项目不变的规则写在 `docs/CONSTITUTION.md`——技术边界、依赖准入、质量红线、数据真伪。每次开工先读，任何任务不得违背，修改须经用户批准并记变更。总纲管所有项目，宪法管这一个项目。

**检查点提交**：每完成一个可验证的子步就提交（一次提交一件事，说明写改了什么、为何改），失败时随时退回上一个可测点，不必推倒重来。

**项目备忘（PROJECT_MEMO）**：每次开始新任务前先读 `docs/PROJECT_MEMO.md`；技术栈、接口索引、假实现边界、待决问题有变的，当次更新，过时条目删除或标失效。

**总计划与按次计划**：先用 templates/master-plan.md 在 `docs/plan/PLAN.md` 写总计划——把本轮目标（立项必做、差距清单等）拆成编号步骤，**每次为一步**，每步写清如何验收。轮到哪一步，就用 templates/session-plan.md 写该次计划（`docs/plan/<步骤号>.md`）：本次改哪些文件、如何验收，完成后回填勾掉。之后一步能搞定的小增补，顺延编号追加（见"增补与新一轮迭代"）。下任务时直接引用计划段落，不靠翻聊天记录。

**计划—执行—核对**：计划（改哪些文件、完成哪条验收、如何自测）→ 执行（只在给定范围内修改）→ 核对（运行自测，对照预期；失败则带着报错回到计划，收紧范围或改写验收后再试）。

**合并纪律**：模型生成的改动，合入主分支前必须通读 diff；只写"已审查没问题"不算审查。审查看四点：目录（有无塞入用不到的模板、错误语言栈）、密钥、与书面约定是否一致、依赖是否真实。

**依赖幻觉检查**：模型可能引用不存在的库或过时接口。以能安装、能运行为准，不以生成文本里写了为准。

**临时假实现**：外部服务或未完成模块用固定返回值顶替时，必须在接口约定、代码注释与备忘三处标明，并写明替换时间。未标明的假实现会在归档时被误当作真实实现。

**排错五项**：修任何 bug 前先写齐——现象（状态码/文案/退出码）、期望（按约定应当怎样）、日志原文（不截断异常名与路径）、相关文件（含刚改过的提交）、已尝试（命令与结果）。然后先判断故障层次（环境/输入/业务/对接），再走根因四步（复现→假设→验证→最小修复），才改代码。

**安全最低集（写进每个任务的约束）**：仓库与日志无真实密钥；外部输入服务端校验；需登录的接口服务端强制鉴权；SQL 与系统命令不与用户字符串直接拼接。不写进约束，模型容易为了先跑通而把密钥写进配置或拆掉校验。

## 仓库工件布局

```text
项目根/
├── docs/
│   ├── CONSTITUTION.md     项目宪法（本项目不变铁律）
│   ├── charter.md          立项书
│   ├── requirements.md     需求规格
│   ├── architecture.md     架构说明（模块职责表+选型比选表+需求对照）
│   ├── contracts/          接口约定（每接口一节或一文件）
│   ├── PROJECT_MEMO.md     项目备忘（常读常新）
│   ├── plan/               总计划（PLAN.md）与按次计划（<步骤号>.md）
│   ├── devlog.md           开发日志
│   ├── demo.md             演示说明
│   ├── smoke.md            通检表
│   ├── gaps.md             差距清单
│   ├── acceptance.md       验收自测表（含安全清单）
│   └── final-report.md     结项报告
```

文件名可按项目习惯调整，但工件本身与其内容结构不可缺。各工件骨架见 `templates/`。

## 与本地 skill 的调度衔接

天工管流程与纪律；下列专用 skill（若已安装）干具体的活，合适就用，没有或不适配时按天工自身工序执行：

| 环节 | 可用 skill | 用法 |
|---|---|---|
| 立项前澄清 | grill-me | 写立项书/需求规格前先拷问一轮：给谁用、成功标准、明确不做什么 |
| 需求转规格 | to-spec | 把已有讨论收束成规格文档 |
| 任务拆票 | to-tickets | 把规格/计划拆成带依赖边的任务票 |
| 实现 | implement | 按规格或任务票实现一块 |
| 测试先行 | tdd | 红—绿—重构做增量，对应阶段六自测 |
| 代码审查 | code-review | 沿"规范/Bug"两轴审查改动，对应合并纪律 |
| 领域建模 | domain-modeling | 统一术语与领域模型，对应阶段二/三 |
| 模块设计 | codebase-design | 设计与加深模块接口，对应阶段二 |
| 会话交接 | handoff | 压缩当前会话为交接文档，另起会话继续（交叉审阅、多会话并行） |
| 选题调研 | research | 对外部问题做高信源调研并落档 |
