# 阶段一 · 立项与需求规格

目标：把"做什么、不做什么、怎样算做完"写清，使后续一切生成都有据可依。

## 要做的事

### 0. 起草前先拷问需求

写任何文档前，先用 grill-me（若已安装）对课题拷问一轮：给谁用、成功标准是什么、哪些明确不做。问实了再落笔。

### 1. 圈定最小可交付范围（MVP）
- 与用户确认课题后，把功能分成两列：**必做**（期内能演示、能说明、能验收的最小集合）与**不做**（明确排除，例："完整赛制编排后台"）。
- 范围一经定稿写入立项书；后续不得把"不做"里的内容悄悄加回来。
- 依赖特殊硬件或外部服务而条件不足的，写明用模拟或录屏替代。

### 2. 写用户故事
格式：作为〔角色〕，希望〔能力〕，以便〔价值〕。角色与能力要具体。
- 较差：作为用户，希望系统更智能。（无法核对）
- 较好：作为选手，希望提交源码后看到评测状态，以便知道是否通过。

### 3. 写验收句（可核对）
格式：**给定**〔前提〕，**当**〔动作〕，**则**〔可核对的结果〕。
- 例：给定选手已登录且题目已发布；当提交合法 C++ 源码；则出现提交记录，且状态最终为 Accepted 或 Wrong Answer。
- 每条必做至少一条验收句；形容词不能当验收。

### 4. 起草立项书与需求规格
用 templates/charter.md 与 templates/requirements.md，写清：课题、必做/不做、主路径（贯穿演示的那条业务流程）、分工（到人到模块）、风险与对策。

### 5. 定项目宪法（CONSTITUTION）

用 templates/CONSTITUTION.md，把本项目不变的铁律写成一页：技术边界（允许/禁止的语言框架）、依赖准入（新依赖须过比选并在备忘登记）、质量红线（密钥、校验、假实现标明）、流程红线（未通读不合入）、数据真伪（能否造数据由用户定）。宪法经用户批准后，后续一切任务不得违背；有变走变更记录。

### 6. 交用户改稿
模型可以起草，但"选哪道题、边界画在哪、怎样算通过、能否造数据、密钥怎么处理"必须由用户拍板。起草稿要经用户改到"能按步骤看出过还是不过"，不得把模型生成的长文直接当需求。

## 通过标准（自检）
- [ ] 每条必做都有给定—当—则验收句
- [ ] 不做事项单独成列
- [ ] 主路径一句话说得清
- [ ] 分工到人（谁负责哪块），不写"全员共同完成"
- [ ] 项目宪法已定稿并经用户批准
- [ ] 硬件/外部依赖写明模拟或录屏方案

## 本阶段易错
- 把参考系统的全部功能抄进必做，做不完
- 验收标准只有"功能正常"，无法按步骤核对
- 模型生成的长文直接当需求，没有改到能核对
- 分工只写姓名，不写谁负责哪块
- 依赖硬件或外部服务，却未写模拟或录屏方案
