# 阶段二 · 组成与技术选型

目标：让别人看懂系统有哪些部分、各做什么、如何协作完成主路径；技术选型有据可查。

## 模块图与模块职责表

- 画到"够用"即可：外部有哪些使用者，内部有哪些主要模块，模块之间的依赖方向。不必画完整类图，可用 mermaid 或文字表达。
- 每个模块配套**模块职责表**（templates/architecture.md）：名称、输入、输出、依赖谁、谁负责。没有这张表，图上只剩无法分工的方框。
- 图上出现、却对不上需求规格的模块：删掉或移出本期范围。

## 需求 → 模块对照

在架构说明中加一张对照清单：每条核心用户故事 → 负责模块 → 演示时是否走这条路径。

- 没有负责模块的需求：补模块，或移入"不做"
- 没有对应故事的模块：删

## 技术选型比选表

- 至少两个候选方案，用**同一组固定维度**逐项比较，避免甲谈性能、乙谈外观。建议维度：组内熟悉度（几人写过）、当前环境安装是否便利、与课题示例是否接近、出问题能否一天内定位。
- 必须写：入选理由 + **放弃落选方案的理由**。只写一个技术名称，不算完成选型。
- 不因"最新"而选型。
- 入选方案写主要风险（如仅一人掌握、依赖外部服务）及对应处理办法。

## 一次一小步

- 先只要与主路径对应的模块名单，核对无误后再补依赖与职责表。
- 先确定主路径模块，最后才考虑缓存、监控等可选项。
- 不要一次向模型索要"完整企业级架构"——那会引入大量用不到的中间件。

## 通过标准（自检）
- [ ] 核心需求均有负责模块，不存在对不上需求的空模块
- [ ] 每个模块有输入/输出/依赖/负责人
- [ ] 选型比选表 ≥2 候选、维度一致、有放弃理由、有风险对策
- [ ] 需求→模块对照表完整

## 本阶段易错
- 架构图只有方框，没有模块职责表与依赖方向
- 只写一个技术名称，没有比选表与放弃理由
- 一次生成"完整企业级架构"，出现大量用不到的中间件
