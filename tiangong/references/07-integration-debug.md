# 阶段七 · 贯通验证与排错

目标：把各模块接成一条可走通的路径；快速通检兜底；致命问题当日清零。

## 拼接时常见断裂（按此排查）

- **字段不一致**：两端对同一概念用了不同名称或大小写
- **时序假设不一致**：一方当作同步返回，另一方依赖事后回调
- **环境问题**：端口被占用、工作目录不正确、依赖服务未启动
- **脏数据**：上次测试留下的记录仍在，导致第二次必失败

## 快速通检（smoke test）

- 一小套用例，确认主功能没有当场失效：**不少于 5 条，其中至少 1 条异常路径**。
- 通检表（smoke.md）：编号、步骤、期望、实际结果、是否通过。主路径条目的步骤对上演示说明的步骤编号。

## 缺陷分级

- **致命（当日清零）**：主路径不可用、数据损坏、明显安全漏洞
- **重要（交付前清零）**：功能受损，或文档导致他人无法启动
- **其余**：归档遗留，并对照立项时写明的"不做"范围说明

## 排错五项（修任何 bug 前先写齐）

1. **现象**：实际看到什么——状态码、文案、退出码
2. **期望**：按约定或验收标准，这次操作应当怎样
3. **日志**：标准输出、错误输出的原文，不截掉异常名与文件路径
4. **相关文件**：出问题的路径；刚改过的提交说明
5. **已尝试**：做过的命令与结果，避免重复已试过的步骤

缺一项，修改建议往往对不上机器上真正发生的事。只说"不好使"不写日志与期望，是排错大忌。

示例写法：

```text
现象：POST /api/submissions 返回 500
期望：201 且含 submission_id
日志：（粘贴终端最后 30 行）
相关文件：services/submission/create.py
已尝试：重启服务；改用约定中的示例 JSON
仍失败：日志出现 problem_id 外键错误
```

## 先定故障层次，再改代码

- **环境层**：依赖未安装、端口占用、权限不足
- **输入层**：请求体未能通过校验
- **业务层**：不允许的状态迁移、权限拒绝
- **对接层**：下游超时、回调未到达

尚未判断故障在哪一层就改业务代码，容易把环境问题掩盖掉。

## 根因四步（定层之后、改码之前）

1. **复现**：找到最小可复现的操作序列；不可复现的先解决复现，不靠猜
2. **假设**：列出可能根因，各归到环境/输入/业务/对接某一层
3. **验证**：一次只验证一个假设——用日志、最小实验或临时输出证实或排除
4. **最小修复**：只改已证实根因的那一处；改完跑通检，确认未弄坏他处

症状消失不等于根因消除：没走完四步的"碰巧好了"，通检一跑还会回来。

## 修复纪律

- 在约定范围内替换临时假实现。
- 修复不大范围改动，防止弄坏已经走通的路径。

## 通过标准（自检）
- [ ] 通检 ≥5 条、含 1 条异常路径，全部通过
- [ ] 致命问题当日清零
- [ ] 联调记录归档（含：纪律约束有没有拦住这次出错）

- 通检全是成功路径，没有异常用例
