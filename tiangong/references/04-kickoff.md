# 阶段四 · 工程起步

目标：仓库能按同一份 README 跑通首跑；留下可追溯的 Git 痕迹。模型生成空项目很快，本阶段的功夫在通读改动、改到能跑、把忽略规则与提交记录写清楚。

## README

用 templates/readme.md 骨架，写清：安装依赖、启动、停止、必要环境变量。隔一段时间或换一台机器，仍应能按该说明跑通。仓库最多留不含秘密的 `.env.example`，并在 README 写如何复制成 `.env`。

## .gitignore

不得进仓库的（通常写入 .gitignore）：

- **依赖目录**：`node_modules/`、`__pycache__/`、`.venv/` 及常见安装产物——依赖应由清单文件重装
- **敏感信息**：含令牌、密码、私钥的文件；本机环境文件（`.env`）
- **构建与本地产物**：构建输出、日志、编辑器缓存、系统垃圾文件；实验类另加数据集缓存、模型权重、中间结果（体积大且可再生或另存）

每一条（或每一类）在文档中写清忽略原因。

## 小步提交

- 一次提交一件事：补忽略规则、写启动说明、加探活接口、删无关模板目录……不把整天改动塞进一次 `update files`。
- 提交说明写清改了什么、为何改。例："补探活接口，便于首跑确认进程已启动"。
- 初始起步至少 3 次高质量提交，每次对应一件可说清的任务。

### 分支与提交规范

- 分支：每块工作开独立分支，命名 `feat/<模块>-<事项>`、`fix/<…>`、`docs/<…>`；改完经审阅合回主分支。单人项目在动大改前也开分支，失败可整支弃掉。
- 提交说明统一格式：`feat|fix|docs|test|chore: 一句话说清改了什么`，必要时补一行为何改。
- 合并说明（PR 或等价记录）写四样：改了什么、为何改、如何验证（自测命令/通检编号）、影响面（动了哪些模块）。

## 通读改动（本阶段重心）

"能启动"只说明没有立刻崩溃，并不说明目录、依赖、示例接口是否合理。初始脚手架合入主分支前：

1. 通读全部 diff（`git diff` 或等价对照）
2. 检查：
   - **目录**：有无塞进用不到的巨型模板、错误的语言栈
   - **配置与密钥**：有无把真实密码、令牌写进仓库
   - **与约定一致**：示例接口或脚本入口是否符合阶段三的书面约定（数据路径、评测命令与输出）
   - **依赖**：有无不认识、装不上、明显无关的包；**依赖幻觉**——模型可能引用不存在的库或过时接口，以能安装、能运行为准
3. 写审查纪要（可并入开发日志）：审查人、时间、所看提交、问题列表、是否已修。只写"已审查没问题"不算审查。

## 与模型配合

让模型只改指定目录；合入前仍由人（或专门的审阅会话）通读改动。**未通读的改动不要合入主分支**——减少把明显问题带入后续各阶段。

## 通过标准（自检）
- [ ] 按 README 文字可独立完成首跑，看到约定输出
- [ ] .gitignore 覆盖依赖目录与敏感文件，逐条有理由
- [ ] ≥3 次小步提交，说明具体不空泛
- [ ] 审查纪要能看出已通读初始改动

## 本阶段易错
- 脚手架生成后无人通读即宣布完成
- README 无法按文字独立启动
- 密钥或 `.env` 被提交进仓库
- 提交次数凑够但说明空泛，或一次提交塞进互不相关的多项改动
