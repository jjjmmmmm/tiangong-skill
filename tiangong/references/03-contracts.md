# 阶段三 · 数据与调用约定

目标：主路径要持久化什么数据、模块间怎么调用，写成仓库里的书面约定；并建立项目备忘。

## 数据模型

- 先画支撑主路径的实体（或数据表）与字段，再补次要内容。实验类课题可按数据切片、指标记录等对象来写，不必套用 Web 分层。
- 对照需求删掉用不到的表与字段——模型容易面面俱到，主路径实体反而含糊。
- 库表、接口、前端三处字段名必须一致；暂时无法统一的，另做一张字段对照表写明三处名称的对应关系。

## 接口约定

写入仓库（docs/contracts/），供各端共同遵守。每个接口至少写清：

- 路径与方法、参数
- **成功一例**（完整请求 + 响应）
- **一类常见失败**（状态码与错误体）
- 需登录的写如何携带身份；列表有分页的写分页参数

未写明的行为不得各自猜测。

示例写法（评测机取下一题）：

```text
GET /api/judge/next
Authorization: Bearer <token>

200 → { "task_id": "t-1001", "language": "cpp", ... }
204 → （当前无任务）
```

## 临时假实现

- 外部服务或未完成模块可用固定返回值暂时顶替，但必须在接口约定、代码、备忘三处标明，并写明**第几阶段替换为真实实现**。
- 未标明的假实现，归档时会被误当作已接真实实现。

## 项目备忘（PROJECT_MEMO.md）

- 为什么写：对话越长，模型越容易丢掉早先约定或混入已作废结论；备忘是仓库中相对稳定的约定。
- 内容：技术栈、主路径接口索引、临时假实现边界、待决问题列表。
- 规则：每次开始新任务前先读备忘；过时条目删除或标失效。

## 总计划与按次计划

- 先写总计划：`docs/plan/PLAN.md`（templates/master-plan.md），把立项必做、差距清单或本轮目标拆成编号步骤，**每次为一步**，每步写清如何验收。
- 轮到哪一步，就写该次计划：`docs/plan/<步骤号>.md`（templates/session-plan.md），本次改哪些文件、如何验收；完成后回填勾掉，并同步更新总计划中该步的状态。
- 之后的小增补：在总计划末尾顺延编号追加，续写按次计划；量大或要开新一轮迭代时，按总纲"增补与新一轮迭代"处理。
- 接口约定相对稳定，规定字段与调用形态；按次计划只服务本次要改的那一步。两份材料都入仓库，不得只留在对话里。

## 给模型哪些材料

- 优先提供：备忘中与本任务相关的段落、本任务允许修改的文件、报错原文或走查失败的那次请求与响应。
- 少提供：无关文件整合、超长对话粘贴、与本任务无关的旧结论。
- 原则：材料不是越长越好，与当前验收相关的信息须准确。

## 通过标准（自检）
- [ ] 约定覆盖主路径；每个接口有成功例与失败例
- [ ] 字段三处一致，或有对照表
- [ ] 假实现已标明并写明替换时间
- [ ] 项目备忘已建立且可继续维护
- [ ] 总计划已建立，每步可验收

## 本阶段易错
- 接口约定只有成功例子，未写失败时返回什么
- 约定只存在于聊天记录，仓库中没有项目备忘
- 临时假实现未标明
